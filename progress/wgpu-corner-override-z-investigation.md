# wgpuレンダラー「コーナーオーバーライドz±5問題」の調査結果(v0.5.0-Alpha-8f)

## 症状の再掲

`openttd-tunnel-portals.md`(v0.5.0-Alpha-8d追記)で報告した不具合: `pushCornerOverrideChunk`で送るコーナーオーバーライドのZ座標の絶対値がおよそ5を超える範囲まで含むと、そのタイルの地形生成(`build_tile_overrides`→`tile_generate.wgsl`)が標高を正しく反映しなくなる(色のグラデーションは変わるが高さが一切上がらない)というもの。当時はブラウザ実機での`window.__webgpuLayer.pushCornerOverrideChunk`直接呼び出しによる二分探索で再現・特定したとされ、`cornerDiffsFromField`に`bounds`引数を追加し山岳トンネルシナリオの書き出し範囲をz=-4..4へ絞る回避策で凌いでいた。

## 検証手順

1. **ネイティブ再現バイナリ(`z_repro.rs`)**: `renderer/renderer_wgpu/src/bin/`にz座標の絶対値を変えながら`build_tile_overrides`とコンピュートシェーダ出力を比較する検証バイナリを作り、ネイティブ(CPU/wgpu native backend)でまず再現を試みた。
2. **エントリ数・座標の二分探索**: オーバーライドの件数、z座標の絶対値、チャンク境界のまたぎ方を変えながら、`build_tile_overrides`が返すフラット配列(`[local_index, height, ...]`)が期待値とバイト単位で一致するかを確認した。`edit_check.rs`(既存の検証バイナリ)が保証するCPU-GPU一致の範囲を、より広いzレンジへ拡張する形で検証した。
3. **wasmデバッグAPIの追加**: ネイティブでは再現しなかったため、ブラウザで実際に動いているwasmインスタンスの内部状態を直接読み出すデバッグAPIを`renderer/renderer_wgpu/src/lib.rs`の`CanvasRenderer`に常設した:
   - `debugTiles()` — 常駐タイル一覧と、各タイルに実際に適用された`build_tile_overrides`の生出力(オーバーライドエントリそのもの)をJSONで返す。
   - `debugOverrideStore()` — 編集オーバーレイの生の格納状態(チャンクごとにlocal_index昇順で整列)をJSONで返す。「保存されている編集」と「タイル生成時に実際に適用された編集」の食い違いを追うため。
   - `debugReadTileSamples(kx, kz, lod)` — 常駐タイルの`samples`バッファ(コンピュートシェーダが書き込んだ生の標高グリッド)をGPUから直接readbackする(`samples`バッファに`COPY_SRC`を追加し、ステージングバッファ経由で`map_async`→`Uint32Array`化)。
4. **samples readbackとスキャンライン比較**: z=-4..4に絞った(旧回避策あり)ケースと絞らない(z非依存の全域尾根)ケースの両方でタイルを生成させ、`debugReadTileSamples`で標高グリッドを直接readbackして比較した。さらに描画結果そのものも、両ケースの重なるz範囲でスキャンライン単位の画素比較(diff)を取った。

## 結論

- `build_tile_overrides`のエントリ数・座標・snap先local_indexは、z座標の絶対値によらずネイティブ・wasm双方でバイト単位で一致した。
- `debugReadTileSamples`によるGPU samplesバッファの直接readbackも、期待される標高グリッドとバイト単位で一致した。
- bounds有り(z=-4..4)/無し(z非依存の全域尾根)の2つのオーバーレイを、重なるz範囲で描画してスキャンライン差分を取ったところ**差分は0(ピクセル完全一致)**だった。
- つまり**データ経路(オーバーレイ構築→GPUバッファ→シェーダの二分探索→描画)は正しく、wgpuレンダラーに欠陥は存在しない**。
- 当時「不具合が直った」ように見えた原因は光学的な誤診断だった: 山岳トンネルシナリオの尾根はzに依存しない(全z共通)帯状の山で、しかも1段/セルのなだらかな勾配(1-Lipschitz)だったため、勾配区間は段丘状の崖(テラス)を作らず滑らかに繋がる。真等角投影(true isometric)では西向きの斜面がほぼエッジオン(視線に対してほぼ平行)に見えるため、長い尾根は単なる平らな色帯にしか見えない。z=±4でboundsを切ると、その端(z=±4)でのみ標高が急に0へ落ちる**テラス状の端面**が生まれ、そこだけが陰影のついた崖として視認できたため、「boundsを絞ったら山が現れた」ように誤認された。

## 対処

- `sim/debugScenarios.ts`の山岳トンネルシナリオの尾根自体をz依存にした: `cornerHeightAt(x, z)`が`|z|<=4`のときだけ隆起し(x方向は従来どおりの山型)、それ以遠は標高0を返す局所的な丘にした。これにより尾根自体に(z方向にも)テラス状の端面が生まれ、真等角投影でも隆起したシルエットとして視認できる。
- 上記の変更により`fieldBounds`(z=-4..4への絞り込み)は不要になったため、山岳トンネルシナリオの`DebugScenarioWorld.fieldBounds`指定を撤去した。
- `bounds`パラメータ自体(`CornerDiffsBounds`/`cornerDiffsFromField`)は削除していない。レンダラー側の不具合回避としては不要だが、大きなマップで手組み地形の範囲が狭いシナリオなど、転送量を減らす最適化としては正当な用途が残るため存続させる。
- `debugTiles`/`debugOverrideStore`/`debugReadTileSamples`の3つのデバッグAPIは、コーナーオーバーライドまわりの今後のブラウザ側診断のために`renderer/renderer_wgpu/src/lib.rs`に常設したままにする(削除しない)。

## 残る教訓

- ブラウザでの目視確認だけで「レンダラーの不具合」と断定しない。今回のように**1段/セルのなだらかな勾配+真等角投影の組み合わせ**は、見た目上「平坦」に見えても標高データ自体は正しいことがある。
- 「回避策を入れたら直って見えた」は、回避策が本当に原因を取り除いたことの証明にはならない。回避策の副作用(今回で言えばboundsの端に生まれるテラス)が別の見た目の変化を生み、それを「直った」と誤認しうる。
- レンダラーの内部状態(オーバーレイの適用状況、GPUバッファの生データ)を直接readbackできるデバッグAPIを用意し、ピクセル値・スキャンライン差分・バッファ内容といった**数値で検証する**ことで、今回のような誤診断を避けられる。目視確認は最終確認の位置づけに留め、疑わしい場合は必ず数値検証を先に行うこと。
