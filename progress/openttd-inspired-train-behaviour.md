# OpenTTD流の列車挙動の輸入設計（構想）

## Decision
- OpenTTD の列車挙動を輸入する。**本プロジェクトは OSS 公開予定でユーザーが GPL 化を許容**しているため、OpenTTD ソースコード（GPL v2）を**教科書として直接精読し、挙動仕様を抽出して TypeScript で再実装**する方針（2026-07-20 更新。C++→TS のため逐語移植はそもそも不可能、挙動の忠実な再現が目標）。
- ソース精読の対象: `src/pbs.cpp`（経路予約）、`src/train_cmd.cpp`（走行・停車処理）、`src/pathfinder/yapf/`（経路探索）。抽出した仕様は progress/ に記録して実装の根拠にする。
- 参照した調査結果: PBS（path-based signalling）/ YAPF（ペナルティ付きA*）/ 制動距離モデル / 瞬時反転 / ホーム長と荷役の関係。出典は本ファイル末尾。

## 輸入する概念と現状のギャップ

### 1. 経路予約（PBS）— 最優先
- OpenTTD: 列車は「次の safe waiting point（信号手前・行き止まり・車庫前）まで」の経路を丸ごと予約してから進む。予約できなければ直前の安全点で待つ。後方の予約は列車後端が抜けた時点で解放。分岐の直後は安全点にしない（分岐を塞いで待たない）。
- 現状: セル占有(trail)+経路全体(route)をゆるく相互参照する方式。信号前の衝突判定はヒューリスティック（id比較など）でデッドロックをその場しのぎしている。
- 輸入案: `route` を「予約」として一級市民化する。
  - 予約単位: 現在地→次の safe waiting point（次の信号セルの手前 / 分岐の手前 / 目的駅の停止位置）
  - 予約が取れない場合はその場（=直前の安全点）で停止して待つ。イベント駆動で再試行
  - 通過済みセルの予約は後端通過時に解放（trail と統合できる）
  - 「出発前に競合区間を丸ごと予約」により、双方向ホーム・単線でのデッドロックが原理的に消える → 既存の id 比較デッドロック回避は削除できる

### 2. ペナルティ付き経路探索（YAPF-lite）
- OpenTTD: A* に「カーブ」「赤信号（連続赤は二次関数的に急増）」「予約済み区間」「勾配」等のペナルティを加算。渋滞回避が自然に生まれる。
- 現状: 素のBFS（最短セル数）＋左側通行のタイブレークのみ。
- 輸入案: BFS→コスト付きダイクストラ/A* に置換し、まず3項目だけ:
  - カーブペナルティ（45度: 小、90度相当: 大）
  - 予約済みセルの通過ペナルティ（大。回避可能なら避け、不可避なら待つ）
  - 赤信号（=予約が塞がる見込みの信号）ペナルティ
  - 左側通行は「進行方向右側セルに小ペナルティ」として表現し直せる

### 3. 制動距離ベースの減速
- OpenTTD: 制動距離は速度の2乗に比例。「確保できている予約長」から逆算して減速開始。
- 現状: Alpha-8a で √(2ad) の連続ブレーキカーブ導入済み（方向性は既に一致）。
- 輸入案: 減速目標を「予約の末端」に一本化する（駅停止位置も信号待ちも「予約がそこまでしか無い」の一形態として統一）。速度制御コードが1本になり、駅/信号の分岐が消える。

### 4. 反転
- OpenTTD の伝統仕様は「行き止まり・車庫での瞬時フリップ」。Alpha-9a で導入済みの瞬時反転と同じ方向性。車庫から出る列車は必ず前向き、も一致。
- 2026年導入の後退走行モデルは輸入しない（複雑さに見合わない）。

### 5. ホーム長と荷役
- OpenTTD: ホームより長い編成は停車可・はみ出た車両の荷役が遅い。
- 現状: 停車時間ペナルティ（はみ出し1両につき+50%）で既に同等の思想を実装済み。

## 実装フェーズ案
1. **予約システムの一級市民化**（PBS化）: safe waiting point の定義 → 予約の取得/解放 → 出発前予約。既存の信号衝突ヒューリスティックを削除。シナリオテスト（すれ違い・双方向ホーム・環状線）で固定
2. **YAPF-lite**: コスト付き探索への置換（予約ペナルティ連携）
3. （任意）加速の物理モデル化（出力・重量ベース）— 車種差別化と同時にやると効果的
