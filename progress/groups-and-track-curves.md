# v0.3.0-Alpha-2: 線路の曲線化・車両の向きの連続化・運用グループ

## 1. 斜め線路と直線のつなぎ目（描画）

### 症状

直線と斜めが切り替わるセル（例: W と NE が接続）で、つなぎ目が汚かった。

### 原因

`buildCellTrackParts` が「セル中心から各境界点へ伸びる直線の腕」を接続方向のぶんだけ
並べる作りだったため、2本の腕がセル中心で45°に折れていた。折れ点では
内側のレールが重なり、外側のレールには切り欠きができる。加えて腕の長さが
直交0.5・斜め0.707と異なるため、枕木の間隔も直線と斜めで揃っていなかった。

### 対応

接続がちょうど2方向のセルでは、**境界点Aからセル中心を制御点として境界点Bへ抜ける
2次ベジェ**を中心線とし、その曲線に沿ってバラスト・レール・枕木を敷くようにした。

- 境界点は「隣接する2セルの中心の中点」で、直交でも斜めでも隣接セルと必ず共有される。
  曲線にしてもセル間で線路が途切れない
- 2方向が正反対（＝直線）なら1セグメントで済ませる。斜めの直進（NE-SW など）も直線扱い
- 枕木は腕ごとではなく**中心線の弧長**を等分して配るので、直線でも斜めでも間隔が揃う
- 分岐（3方向以上）と行き止まり（1方向）は従来どおり中心からの直線の腕。
  中心にバラストのパッドを置いて腕どうしの継ぎ目を埋める

## 2. 走行中の車両の向きが飛ぶ

原因は2つあり、どちらも独立に効いていた。

### 2-1. 到着tickで lookAt が縮退する

セル到着時に `renderPos` を到達セル中心へ更新する一方 `renderTarget` を更新しておらず、
その1tickだけ `renderPos === renderTarget` になっていた。three.js の `lookAt` は
視線ベクトルの長さが0のとき z 軸を (0,0,1) にフォールバックするため、
**1フレームだけワールド+Z方向を向く**。これが「ガクッと一瞬だけ」の正体。
セル到着のたびに起きていたが、斜めでは誤差が45°になるので目立っていた。

対応: 到着時に次のセル（無ければ進入方向の延長線上）を `renderTarget` に入れる。
さらに描画側では `renderTarget` への `lookAt` をやめ、後述の台車ベースの向きを使う。

### 2-2. 向きをポリラインのセグメント方向から取っていた

`carPositions` の heading は「サンプル点が乗っているセグメントの向き」だったため、
折れ点を跨いだ瞬間に階段状に飛んでいた。

対応: 前後の台車位置（弧長 ±`BOGIE_HALF_SPACING`）を結んだ向きから heading を求める。
前台車が先に曲がって後台車が追いつくまでの間に向きが連続的に変わるので、実車と同じになる。
先頭車は前台車が先頭より前に出せないので0でクランプするが、両端の点はポリラインに
沿って連続に動くため向きは飛ばない。

### 2-3. 走行線そのものを線路の中心線に載せた

上の2つを直しても、**列車はセル中心を直線で結んだ線**を走り、**レールは曲線**という
食い違いが残る。カーブの頂点で最大0.125セル（≒3.7m）ずれて、車両がレールから
外れて見える。

対応: `sim/trackPath.ts` を新設し、描画側と同じ「セル曲線」の定義を sim 層でも持つ。

- `pathPointAt(prev, curr, next, nextNext, progress)` — `renderPos` をこの曲線上で求める
- `curvedTrainPolyline(...)` — `carPositions` が辿るポリラインも曲線に載せる

**重要な性質**: prev/curr/next が同一直線上に等間隔で並ぶ（＝直線区間）場合、
このベジェは「セル中心間の線形補間」と厳密に一致する。したがって直線区間の挙動は
1ビットも変わらず、既存の停止位置テストなどに影響しない。

### 落とし穴

`curvedTrainPolyline` の最初の実装では、`progress > 0.5` のとき先頭が
**次のセルの曲線の前半**に乗っていることを見落とし、現在セルから辿り始めていた。
その結果 `progress` が 0.5 を跨ぐ瞬間にポリラインの弧長が半セルぶん飛び、
後続車の位置と向きが一気にずれて**修正前より悪化**した（1tickあたりの向きの変化が
2.1° → 13.6°）。先頭がどのセルの曲線上にいるかで場合分けして繋ぐ必要がある。

### 計測結果（直線→斜め→直線のジグザグ、最高速100km/h、dt=1/60）

| | 1tickあたりの向きの最大変化 |
| --- | --- |
| 旧実装 | 45°（セル境界での段差） |
| 台車ベースの向きのみ | 2.09° |
| ＋走行線を中心線へ | **0.91°** |

回帰テストは `sim/heading.test.ts`。

## 3. 運用グループ（軽量なグループダイヤ）

### 方針

「駅ごとの発車時刻を持つ時刻表」ではなく、OpenTTDの**共有オーダー + separation**に
近い形にした。ゲーム内時計の絶対時刻に停車時刻を割り付けないので、遅延の伝播や
時刻の再計算を扱う必要がなく、実装も運用も軽い。

- 複数の列車を1つのグループにまとめ、**運行表をグループで共有**する
- グループに**発車間隔（headway）**を設定すると、駅を発車するときに
  「同じグループの列車が同じ駅を発車してから headway 秒経っているか」を見て、
  足りなければその場で待つ。これだけで団子運転が自然にほどけて等間隔になる

### 実装

- `sim/groups.ts` — 純粋関数（`effectiveSchedule` / `headwayHoldSeconds` /
  `departureKey` / 名前・色の採番）
- `SimWorld.groups` と `SimWorld.groupDepartures`（「グループ×駅」→ 最終発車時刻）
- `TrainRuntime.pendingDepartureFrom` — 停車を終えて発車待ちの駅id。
  発車間隔の判定は**この間だけ**行う。線路上で経路や予約を待っている状態
  （`Waiting for Path` など）に適用してしまうと、本来の閉塞待ちと区別が付かなくなる
- 実際に発車した時点で `groupDepartures` を更新し `pendingDepartureFrom` をクリアする
- 単独の列車がグループにいても、自分の前回発車からは1周ぶんの時間が経っているので
  待たされない（自分の記録で自分が止まることはない）

### UI

- 右上「運用」パネル: グループの一覧、名前の変更、発車間隔（なし/15/30/45/60/90/120秒）、
  共有運行表の表示、運行表の消去、グループ削除
- 列車インスペクタの「運用」: 単独／既存グループへの所属切り替え、
  この列車の運行表を引き継いだ新規グループ作成
- グループ所属中に「運行表を編集」で駅をクリックすると、**グループの共有運行表**に追加される
- グループのラインカラーが3D上の車両の帯にも反映されるので、地図を見るだけで系統が分かる
- グループを削除すると、所属列車は共有運行表を自分の運行表として引き継いで単独運用に戻る

### セーブデータ

SaveData **v9**。`groups` と `groupDepartures` を追加。v8以前からは空グループで移行する。

## 4. 既知の課題（未対応・前回から継続）

- 交換設備の無い単線区間での正面デッドロック
- 斜め2セルの終端駅からの折り返しに失敗することがある
- 列車種別（快速・急行などの通過運転）は今回のスコープ外
