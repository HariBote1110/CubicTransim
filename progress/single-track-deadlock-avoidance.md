# 単線デッドロック回避: 「分岐点の手前は安全点」ルールの廃止

## Decision
- `pbs-reservation-refactor.md` で導入した safe waiting point のルール5「次セルが分岐点なら安全(分岐点自体には
  進入・停止しないが、その手前では停止できる)」を`src/sim/reservation.ts`の`isSafeWaitingPoint`から削除した。
- 削除理由: このルールは単線運用でデッドロックを起こす。対向する2列車が単線の共有区間の両端でそれぞれ
  「分岐点の手前」まで予約を取ってしまうと、互いに相手の区間へ予約を延長できず永久に睨み合う。
- OpenTTDのPBSにならい、待機が許される位置は「信号に守られた位置・駅・車庫・行き止まり」だけに限定した。
  残るルールは: 次セルが信号セル / 自セルが駅 / 自セルが車庫 / 次セルが無い(行き止まり)。「分岐点そのものには
  停止しない」ルール(`isJunction(cellData)`→不可)は維持。
- 結果として、単線区間には「次の信号または駅まで一括で予約できた列車」しか進入できなくなった。交換設備
  (passing loop)は分岐・合流の両方の入口に信号が必要になる(OpenTTDと同じ仕様)。

## レイアウト側の対応(既存テストの信号追加)
- `src/sim/passing-loop.test.ts`の受け入れシナリオは、西側分岐(10,0)は既存の信号(11,0)で守られていたが、
  東側合流点(15,0)を守る信号が無かった。ルール削除後、合流点(15,0)そのものが「次セルに信号がある」ことを
  理由に安全点とみなされてしまい(次の(16,0)~(24,0)は素通しの単線であるため、実質的に合流点(15,0)上で
  列車が滞留する)、これが待避線側の経路をも塞いでしまい恒久デッドロックした。
  - 誤った初期対応として信号を合流点の**先**(16,0)に置いたが、これは合流点(15,0)自体を安全点にしてしまい
    (次セル16,0が信号のため)、同じ問題を再現した。
  - 正しい対応: 信号は合流点の**手前**(14,0、東向き)に置く。これにより安全点は合流点そのものではなく
    その1つ手前のセルになり、旧ルールが自動的に達成していた「分岐点そのものには居座らない」挙動を、
    明示的な信号配置で再現できる。
- `src/sim/pbs-reservation-scenarios.test.ts`の「分岐の直前で待たない」シナリオは元々分岐・合流点の両方に
  信号を備えたレイアウトだったため、修正なしでそのまま通った。

## 単線でのデッドロックの調査結果(報告事項)
新しい規則のもとでも、「2本の列車が単線に閉じ込められて双方が動けなくなる」ケースは起こりうる。

- **起きる条件**: 単線区間の途中に安全点(信号・駅・車庫)が1つも無く、かつ区間の両端の駅に対向列車が
  それぞれ最初から在線している(=互いの目的駅を相手が塞いでいる)場合。
- **理由**: 途中に安全点が無いと、`findSafeSegmentEnd`は経路の途中に一切の安全点を見つけられず、
  「始点から目的駅まで」を1回のtryReserveで丸ごと予約する以外に道が無い。目的駅のセルは対向列車が
  (同じ理由で動けず)恒久的に保有し続けるため、双方とも目的駅を含む区間を一度も予約できない。
- **これは今回のルール変更が原因ではない**: このケースには分岐点が存在しないため、旧ルール(分岐点の
  手前を安全点にする)は最初から無関係で、削除前のコードでも同一条件で同じ結果になることを確認した
  (`src/sim/single-track-deadlock.test.ts`で検証。同じレイアウトを旧`reservation.ts`で実行しても
  0本の到着で恒久停止する)。
- **既存の設計判断と整合**: `src/sim/passing-loop.test.ts`の「頑健性: 交換設備の無い純単線での対向列車」
  テストが元々「衝突しないが永久デッドロックでも安全」という基準を採用しており、今回の
  `single-track-deadlock.test.ts`もこの基準に合わせた(到着を要求せず、衝突しないことと恒久停止することを
  検証する)。
- **回避策**: 単線を運用する場合、途中に最低1つの信号(または通過可能な駅)を置き、区間を2つ以上の
  予約単位に分割する必要がある。何も無い一直線の単線は、両端に対向列車が最初から詰まっている限り
  設計上動けない。

## Constraints / Gotchas
- 「次セルが信号セルなら、自セルが分岐点であっても安全」というルール自体は維持している。このルールは
  「信号の1つ手前」だけでなく、「分岐点の直後の信号セルの、その分岐点自身」も安全点にしてしまう
  (`nextData?.signalDir`チェックが`isJunction(cellData)`チェックより先に評価されるため)。信号を
  分岐点の直後ではなく直前に置くレイアウトにすることで、分岐点自体への滞留を避けられる。
