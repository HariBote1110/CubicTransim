# クォータービュー特化レンダラー(WASM + WebGPU)要件定義とプロトタイプ仕様

## 位置づけ

three.js ベースの現行描画を、Rust + wgpu を WASM に載せた自前レンダラーへ置き換える構想。
根拠となる実測は map_scale_research/notes/generation-scaling.md(追記2まで)。
ボトルネックは GPU 性能ではなく「CPU 側のチャンクジオメトリ生成とノイズ評価」なので、
このレンダラーの価値は速度そのものではなく、以下のアーキテクチャ転換にある:

1. 地形ノイズ評価を GPU(コンピュートシェーダ)へ移し、CPU のチャンク生成を原理的に廃止
2. クリップマップ/四分木 LOD により全図ズームアウト(16K 全体を1画面)を成立させる
3. 固定クォータービューの数学的特典(ソート不要の描画順・閉形式ピッキング・ベイク影)を全面利用
4. ジオラマ物(木・家・レール片・車両)の全面インスタンシング

## 性能目標(厳格・確定値)

計測環境は「このMac(Apple Silicon 統合GPU)・Chrome安定版・1600×900キャンバス・極大16385マップ」
に固定する。すべて **リリースビルド(wasm-pack --release)** で計測し、数値は
「中央値 / p99」を1万フレーム以上のサンプルで取る。専用ベンチハーネス(後述)の自動計測のみを
成績として認める(目視・体感は不可)。

| # | 項目 | 目標 | 備考 |
|---|---|---|---|
| T1 | フレーム時間(静止時) | 中央値 ≤ 2ms / p99 ≤ 4ms | CPU+GPU合算(タイムスタンプクエリ) |
| T2 | フレーム時間(最大速度パン中) | 中央値 ≤ 4ms / p99 ≤ 8.3ms | 120fps相当を p99 で満たす |
| T3 | ヒッチ | 16.6ms 超のフレームが 1万フレーム中 **0** | パン・ズーム・地形編集込み |
| T4 | 全図ズームアウト(16K全体が1画面) | 中央値 ≤ 4ms / p99 ≤ 8.3ms | クリップマップLODの合否そのもの |
| T5 | ズーム連続遷移(全図⇔1セル100px を2秒で往復) | T3 と同じ(ヒッチ0) | LOD切替のポップ許容、ストール不可 |
| T6 | 初期表示(new Game→初フレーム) | ≤ 300ms | ノイズはGPU生成なので原理的に可能 |
| T7 | 新規タイル可視化遅延(パンで未生成域に入る) | ≤ 50ms(3フレーム) | 生成待ちの空白タイル表示は許容しない |
| T8 | 地形編集の反映 | 次フレーム(≤1フレーム遅延) | 差分オーバーレイ更新→再サンプル |
| T9 | GPU 常駐メモリ | ≤ 256MB | タイルピラミッド+インスタンス+アトラス込み |
| T10 | WASM ヒープ | ≤ 128MB | 16K・町1万・列車1000編成の状態で |
| T11 | ドローコール | ≤ 30/フレーム | 種別ごとインスタンシング前提 |
| T12 | インスタンス規模 | 樹木10万・家3万・列車1000編成を同時描画で T1〜T3 維持 | ベンチシーンで検証 |
| T13 | ピッキング | ≤ 0.1ms(閉形式、GPU往復なし) | セル+レイヤ解決まで |
| T14 | ノイズ一致 | TS実装と cornerHeightAt 整数値で **1000万点サンプル一致率100%** | 不一致1点でも不合格 |
| T15 | バンドルサイズ | wasm ≤ 2MB(gzip) | Electron/初回ロードの体験 |

**ベンチハーネス(成果物の一部として必須)**: スクリプト化されたカメラ経路
(静止→最大速パン→全図ズームアウト→往復ズーム→terraform 連打)を再生し、
フレーム時間ヒストグラム・GPUタイムスタンプ・メモリを JSON で吐く。目標との合否判定を
自動で出すこと。これを回さずに「速くなった」を主張しない。

**不合格時の扱い**: T1〜T8 のいずれかが未達の間は three.js 置き換えを行わない
(プロトタイプ棚上げ、原因分析ノートを renderer_research/notes/ に残す)。

## 本実装の要件(プロトタイプの先にあるゴール)

- 対象マップ 16385²、ズーム「1セル≈100px」〜「全図」連続(上記 T1〜T15 を満たすこと)
- 基底地形 = seed 純関数(src/sim/terrainField.ts の4オクターブ値ノイズと**ビット一致**。
  隣接段差1以下の保証を含む。WGSL に移植し、TS 実装と同一 seed で同一整数格子を返すことを
  検証テストで担保する — ここが唯一の「正しさの橋」)
- 編集差分(terrainOverlay.ts の CornerDiffs)は疎オーバーレイ(ストレージバッファ or
  スパーステクスチャ)として GPU 側で合成
- sim との境界: レンダラーは (a) seed/halfExtent (b) CornerDiffs (c) SimWorld スナップショット
  (railMap/stations/trains/towns の描画必要部分) (d) ダーティ通知(チャンク座標)のみを受け取る
  純粋な消費者。ゲームロジックへの逆依存ゼロ。sim 層(TS/Vitest)は無改修
- 描画対象は現行の全部: 段差つき地形・水域・勾配レール・高架 1..3/地下 -1..-3(ビュー切替と
  減光は uniform 1つで)・トンネル坑口・駅・車庫・信号・町タイル・樹木・列車(編成・ピッチ)・
  建設プレビュー
- ピッキング: 逆射影の閉形式でセル座標を返す API(現行の raycast 依存を廃止)
- 実行環境: Chrome/Edge(WebGPU 安定版)+ Electron。WebGPU 非対応環境では現行 three.js に
  フォールバック(両立期間を設ける。三行スイッチで切替できること)

## プロトタイプ(縦切り)スコープ

**目的: 「GPU ノイズ地形 + クリップマップ LOD + パン/ズーム」だけを最短で成立させ、
16K 全図ズームの体験と性能を実証する。** 以下だけを作る:

1. Rust + wgpu + wasm-bindgen のワークスペース(`renderer_research/proto/`。
   *_research 配下 = 使い捨て前提、mainstream への昇格は別途 TDD で)
2. WGSL に terrainField の値ノイズを移植(検証: wasm 側から N 点サンプリングして
   TS 実装と一致することを確認するハーネス。プロトタイプ段階では「目視で同じ地形」+
   数百点のスポットチェックで可)
3. コーナー格子高さ場のタイルピラミッド(例: タイル 256²、LOD は 2x ずつ粗く、
   スクリーン誤差でレベル選択)をコンピュートシェーダで生成、LRU 常駐
4. 頂点プリング地形描画(段差・斜面の見た目は現行の「上面+崖面」に近い簡易版でよい。
   パレットは render/palette.ts の色をベタ移植)
5. 水域の平面、以上。レール・町・列車・編集差分はプロトタイプ対象外
6. マウスでパン・ホイールでズーム(全図まで)。HUD に frame time / 生成タイル数 / GPU メモリ
7. 成果判定(数値): プロトタイプ段階では厳格目標の緩和版として
   (a) T3(ヒッチ0)をパン・ズームで満たす (b) T4(全図)を p99 ≤ 16.6ms で満たす
   (c) T6 初期表示 ≤ 1s (d) T14 ノイズ一致(サンプル数は100万点でよい)。
   ベンチハーネスの骨格(カメラ経路再生+JSON出力)もこの段階で作り、
   本実装の厳格値(T1〜T15)への到達可能性を数値で見積もること

## プロトタイプの技術メモ

- クレート: wgpu 0.20+, wasm-bindgen, winit は使わず canvas + JS イベントを bindgen 経由で
  受ける(React 統合を見据えて)
- 16K の全高さ場は GPU に置かない(16385² × 1B = 268MB)。常に「可視タイル+ピラミッド上位」
  だけを保持
- 値ノイズの格子ハッシュ(mulberry32 風ビット撹拌)は u32 演算のみなので WGSL 移植は素直。
  浮動小数の丸めだけ TS(f64)と WGSL(f32)で差が出る可能性がある → 整数段数への量子化点で
  一致を取る設計にする(cornerHeightAt の返り値レベルで比較)
- 開発ループ: `wasm-pack build` + 素の Vite ページ(ゲーム本体とは独立の
  renderer_research/proto/web/)。ゲームへの統合はプロトタイプ合格後の次フェーズ

## 昇格判定(プロトタイプ→本実装に進む条件)

- 上記成果判定 (a)(b)(c) を満たす実測値が取れること
- WGSL ノイズが TS と cornerHeightAt レベルで一致すること(不一致ならセーブ互換の観点で
  ノイズ仕様の再設計が必要になり、コストが跳ねる — ここが最大のリスク)
- Electron(Chromium)上でも WebGPU が動くこと

## 判断済みの却下案

- WebGPU + TS(WASM なし): 技術的にはこれで足りるが、ユーザーの意向で Rust+WASM を採用
- フルネイティブアプリ化(sim ごと Rust 移植): React/TS 資産(UI・sim・750 テスト)の
  放棄になるため却下
